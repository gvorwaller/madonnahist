Family members can now change their own password on `/app/account`, renamed "Your account" (b0a2dee). Admins can remove access to any account, restore it, and permanently delete throwaway accounts. ### What Was Done
**Your account: change password (b0a2dee)**
- `/app/account` is now "Your account", and the menu link says the same. The page has Your name, Your username, **Change your password** (current, new, new again), and the home-screen help.
- The new password uses the invite rules and wording (`passwordProblem`: 8+ characters, must match). It is refused if it's the same as the current password.
- On success:
  - every session is deleted and this device gets a fresh one, so other devices are signed out;
  - an open invite link is cancelled;
  - the change is audited as `password_change` with no secrets.
- The UPDATE only replaces the hash it verified (`AND password_hash = $old`), so a concurrent admin reset wins and the person gets a 409.
- Rate limit is 5 wrong current-password tries per person per 15 minutes, then 429. Typos in the new password are checked first and don't count.
- A hidden `autocomplete="username"` field makes Safari and password managers update the right saved login.
- `test:invites` gained 22 checks (100 total).

**Accounts: remove access / restore / delete permanently (ba690eb)**
- `/admin/users`:
  - Every row except your own (marked "You") gets a **Remove access** button with a modal confirm.
  - A collapsible **Removed accounts** list has a "No access" badge and **Restore** / **Delete permanently** (also a modal confirm).
  - A green notice banner reports success.
- Remove access:
  - sets `removed_at` / `removed_by`;
  - deletes sessions, and `validateSession` refuses removed accounts as well;
  - sign-in gets the usual "incorrect" message;
  - invites are revoked, and `classify` treats removed accounts as revoked;
  - reset password and invite links are refused until restored;
  - audited as `user_remove` with the username, name and role.
- Restore puts the old password back in force (`user_restore`).
- Delete permanently:
  - works on removed accounts only;
  - writes `user_delete` (username, name, role) and then the DELETE in one transaction;
  - if a foreign key refuses (23503), the page names what blocked it in plain words ("shorthand entries", "corrections", …).
- Guards:
  - You can't remove or delete yourself.
  - You can't remove the last admin who can still sign in. Active admin rows are locked `ORDER BY id FOR UPDATE`, so two admins removing each other at the same moment leaves one.

  - `place_locations.decided_by` becomes **NO ACTION**, because an admin's place decision is content and blanking it would let the automatic re-check overwrite it.

### Key Technical Insight
- **Let foreign keys define "throwaway".** Every content table references `users` with the default NO ACTION, so any account that authored something can't be deleted. New tables (comments, family memories) get that protection just by declaring a plain FK; no allow-list needs maintaining. Only the activity log was switched to SET NULL, because it's a record, not content.
- **Audit the identity before deleting.** `user_delete` stores the username, name and role in `before_value`, because the deleted account's own lines lose their person.
- **Before deploying, check every column that names a user.** A catalog query over `information_schema.columns` matching `user`/`_by` showed every such column has an FK (`narrative_summaries.generated_by` is a model name, not a user).
- **`npx prettier --write` rewrites a whole file here** (the repo has no prettier config). Don't run it on existing test scripts.
- **Safari WebDriver without selenium:** the element key is `element-6066-11e4-a52e-4f735466cecf`; plain `fetch` to safaridriver works fine.
