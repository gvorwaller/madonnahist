### Key Technical Insight

1. **PM2 `restart --update-env` does NOT re-read `node_args` from the ecosystem config.** Only restarts the process with the current registration. To pick up changes to `script`, `node_args`, or `cwd`, you have to `pm2 delete` then `pm2 start ecosystem.config.cjs`. The first deploy hit this: I edited `node_args: '--env-file=.env'`, restart didn't pick it up, health was still red, looked like the env-file approach was broken. Diagnosis path was `pm2 describe` (showed `interpreter args: N/A`) → delete + start → describe again → green. Worth remembering: PM2's "live updates" are limited to env vars.

2. **`node --env-file` is the cleanest way to load `.env` into a PM2'd SvelteKit adapter-node app.** No `dotenv` import, no entry-point wrapper, no PM2 `env_file` plugin. Just `node_args: '--env-file=.env'` with `cwd: '/opt/madonnahist'` so the relative path resolves to `/opt/madonnahist/.env`. Node 20.6+ built-in.

3. **Sourcing `.env` into shell for ad-hoc psql tests is a footgun**. The .env's `PGPASSWORD` (app role's password) bleeds into the environment, and any subsequent `psql -U some_other_role` picks it up via env-var precedence over `~/.pgpass`. That's why my owner-role smoke test initially failed with "password authentication failed" right after I had just successfully created the role with that exact password. Fix: `unset PGPASSWORD` before testing other roles, or use explicit `PGPASSWORD=$X psql ...` per call. The role configuration itself was fine — the test methodology was wrong.

4. **Droplet sibling discovery beats plan assumptions.** Plan locked Decision 2 as "Full Strict + Cloudflare origin cert" assuming siblings already had origin certs installed. Reality: siblings run HTTP-only on :80, zone is on Cloudflare Flexible mode, no `/etc/ssl/cloudflare/` directory exists. Switching plan posture to "match siblings, defer zone upgrade" was faster and more consistent than installing a one-off origin cert for madonnahist alone. The plan called this out as a watch-out — and the watch-out fired. Always discover droplet state before installing infra config.

5. **`pg_createcluster` on Ubuntu's PGDG auto-creates a `main` cluster on :5432.** If you want :5434 only, you have to `pg_dropcluster --stop 17 main` after installing `postgresql-17`. Not a problem, but a step the plan didn't anticipate — added in execution.

6. **Repo visibility decision was a real-world utility/security tradeoff, not just a config flag.** Initially private (default), so the droplet `git fetch` needed deploy-key choreography (per-repo ed25519 + ssh config alias + GitHub deploy-keys settings page). Once we walked through what was actually in the repo (passwords gitignored; calendar content lives in Spaces + Postgres, both auth-gated; droplet IP already public via cs.md in sibling repos), the marginal exposure of going public was zero. Flip → public → `git fetch` just works without any deploy-key dance. Worth remembering that "private by default" isn't always the right end-state for a side project archive.

7. **`form_input` for React-controlled inputs can silently no-op.** DO Spaces' bucket-name field is a `<input type="search">` whose React handler tracks the value via onChange — setting `.value` directly via the form_input tool returned `Set search value to "" (previous: "")` even though I passed "madonnahist". Click-then-type with the `computer` tool worked. Watch for this pattern when driving SPAs.

8. **`/api/health` shape: db gates deploy, spaces is observability.** `db: ok | error`, `spaces: ok | not_configured | error`. The deploy script tolerates `spaces=not_configured` (bootstrap window before credentials seeded) but fails on `spaces=error` (creds present but request failing). This lets the very first deploy succeed before Spaces has been provisioned at all, while keeping `error` as a real signal post-seeding.
