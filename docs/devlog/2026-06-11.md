## 22:00 EST - Droplet Upgrade and PM2 Memory Guard

### Summary
Upgraded the DigitalOcean droplet from 1GB/1vCPU ($6/mo) to 4GB/2vCPU ($24/mo) to resolve recurring OOM kills, and added a PM2 max_memory_restart guard to prevent future kernel kills.

### What Was Done

**Droplet resize (1GB → 4GB)**
- Codex diagnosed the root cause: kernel OOM killed madonnahist twice on 2026-06-11 (01:04 and 15:24 UTC) — the 1GB droplet couldn't handle concurrent OCR review image processing
- Took a live snapshot as safety net before resize (8.07 GB, stored in SFO3)
- Powered off droplet, resized to Basic Regular 4GB/2vCPU/25GB SSD ($24/mo) with downscale-anytime option checked, powered back on
- Verified: 3.8 GB RAM (3.0 GB free), 2 CPUs, zero swap usage, all three PM2 apps online, health check passes
- Same IP retained: 134.199.211.199

**PM2 max_memory_restart**
- Added `max_memory_restart: '2500M'` to `ecosystem.config.cjs`
- Gives madonnahist 2.5 GB before PM2 gracefully restarts it, leaving ~1 GB headroom for gaylonphotos (~95 MB), giftlist (~150 MB), Postgres, and OS buffers
- Deploy script only does `pm2 restart` which doesn't reload ecosystem config — had to `pm2 delete + pm2 start ecosystem.config.cjs + pm2 save` manually on prod to pick up the new setting

### Files Modified
- `ecosystem.config.cjs` — added `max_memory_restart: '2500M'`

### Key Technical Insight
PM2's `pm2 restart <app>` reuses the saved process config from `dump.pm2` — it does NOT re-read `ecosystem.config.cjs`. To pick up config changes (like new `max_memory_restart`), you need `pm2 delete <app> && pm2 start ecosystem.config.cjs && pm2 save`. The deploy script should be updated to handle this, or ecosystem config changes need the manual cycle.
